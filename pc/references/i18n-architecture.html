国际化(i18n)原理与设计 ​

日常开发请看实操规范:i18n-guide.md。本文面向排查问题、理解机制与二次开发。

一、体系总览 ​

技术方案：i18next + i18next-vue，中文原文作为 key、多语言译文为 value 的平铺 JSON，中文为回退语言。

启动时:  内置基础词条 + locale/common + basic_components + screen → 合并进 i18next 初始资源
路由切换: src/permission.js → loadRouteI18n(路由) → 懒加载 views/**/locale/{lang}.json 注入 i18next
语言切换: hooks/locale.js(useLocale) → 骨架屏 → 切 i18next 语言 → Arco 组件同步 → 接口按优先级串行重发
语言存储: localStorage 裸 key `arco-locale`('zh'/'en' 纯字符串)
检测顺序: URL ?lang= → localStorage → cookie → 浏览器语言；回退语言 zh

核心源码职责 ​

文件职责
src/locale/index.jsi18next 初始化、全局四层词条合并、LOCALE_STORAGE_KEY、translateColumns、响应式 getCurrentLanguage
src/locale/loader.js页面级词条懒加载(import.meta.glob)、页面级优先/旧路径回退、缺失 key 记录(localStorage.missingKeys)
src/locale/memory-manager.js翻译缓存记录使用情况、超限自动清理
src/hooks/locale.js无刷新语言切换编排(骨架屏/Arco 同步/接口重发)
src/utils/i18n-refresh.js语言切换后按 P0→P1→P2 优先级串行重发接口
src/utils/arco-locale.jsArco 组件库语言包切换
src/permission.js路由切换时触发 loadRouteI18n(targetRoute)

二、词条分层与加载机制 ​

2.1 两类词条 ​

全局层(启动即全量加载，合并顺序: 内置基础 → common → basic_components → screen)
├─ src/locale/common/            跨页面公共文案
├─ src/locale/basic_components/  基础通用组件词条
└─ src/locale/screen/            大屏公共词条

页面层(进入对应路由时懒加载)
└─ src/views/**/locale/{lang}.json

2.2 页面级懒加载 ​

loader.js 通过 import.meta.glob('../views/**/*.json', { eager: false }) 收集全部页面词条的懒加载句柄(不打包进首屏)；路由切换时 permission.js 按 route.localFilePath 推导出 ../views/<路径>/locale/{lang}.json 加载并 addResourceBundle 注入。

查找顺序：页面级 → 旧版 src/locale/{lang}/ 路径(兼容回退)。旧结构只读不写，新词条禁止放入。

三、热切换设计(无刷新切换语言) ​

hooks/locale.js 的 useLocale() 编排整个流程：

  1. 展示全局骨架屏(避免中英混排闪烁)；
  2. i18next.changeLanguage(lang)，持久化到 localStorage 裸 key arco-locale；
  3. arco-locale.js 同步 Arco 组件语言包(分页、日期选择器等内置文案)；
  4. i18n-refresh.js 更新请求头 lang，并按 P0→P1→P2 优先级串行重发已注册接口(后端按 header 返回对应语言的菜单名等数据)。串行是为了避免并发请求间语言标识错乱；
  5. 隐藏骨架屏。

后端约定：所有接口请求携带 lang header，返回的 menuName 等数据跟随语言。新页面若需接口数据随语言切换，需在 i18n-refresh 中注册对应接口优先级。

四、缺失 Key 策略 ​

  • 生产环境或中文环境：静默回退显示原 key(即中文)；
  • 开发环境且 key 非纯英文：控制台 [i18n] Missing translation 告警；
  • loader 将缺失 key 记录到 localStorage.missingKeys(含来源页面路径)，用于批量补齐。

这套策略配合「中文即 key」的设计：中文永远不缺词，工程上只需保证 en.json 完整(由 pnpm i18n:verify-keys 兜底)。

五、内存管理 ​

memory-manager.js 记录每个页面词条的加载与使用情况，缓存超限时按使用频率清理，防止长期使用后词条无限膨胀。相关 API 经 loader.js 导出:getMemoryInfo()、cleanupTranslationCache()、setCacheLimits()。

六、大屏三层架构 ​

大屏采用可选翻译设计：多语言项目(如 shate)建完整 locale，单一语言项目(如 road_634)不建任何 locale 文件——查找自动落空显示原中文，无需代码分支。

查找优先级: 当前页面 locale → library/组件 locale → locale/screen(大屏公共) → 全局 → 原始键名

第一层 src/locale/screen/       layout 组件、通用组件文案(导航菜单/工具栏/星期月份/通用文本)
第二层 screen/library/*/locale/ 业务卡片组件词条(仅含业务专有术语时才建)
第三层 screen/pages/*/locale/   各项目页面词条(按项目决定是否建)

设计要点：

  • layout 组件不建 locale，统一用第一层公共词条；
  • 嵌套 key 用于分类(如 导航菜单.项目概览、组件.Panel.关闭)；
  • 大屏文本需考虑译文长度差与字体适配。

七、Key 设计取舍(中文即 key) ​

优点：中文环境零成本(永不缺词、无需 zh.json)；文案即代码可读性高；新增文案无需先设计 key。

代价：改中文文案 = 改 key，必须同步 en.json(用 verify-keys 校验)；key 冗长；同一中文在不同上下文需不同译法时无法区分(需借助点号前缀分类)。

规则由此推导：代码与词条逐字符一致是本方案的第一纪律。
