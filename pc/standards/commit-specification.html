PC 端 · 提交规范 ​

与 keystone-deliver-ui 的 commitizen + commitlint 配置对齐（2026-09-16 核对）。

commit message 格式 ​

text
<type>(<scope>): <subject>

  • type（枚举，与 .cz-config.js 一致）：

    type含义
    feature新功能
    bug测试反馈 bug 列表中的 bug 号
    fix缺陷修复
    ui界面 / 样式调整
    docs文档
    style代码格式（不影响逻辑）
    perf性能优化
    refactor重构（既非新增也非修复）
    release发布
    deploy部署相关
    test测试相关
    chore构建过程或辅助工具变动
    revert回滚
    build打包
    merge分支合并（仅 commitlint 允许，cz 菜单不出现）

  • scope 必填：commitlint 强规则 scope-empty: never——写模块 / 业务域，如 qual_mgmt、cfg_center、http；

  • subject：≤72 字符（subjectLimit: 72），中文简述，不加句号；header 长度上限校验已关闭，但请自觉精简；

  • body / footer：cz 交互默认跳过，一般不写。

示例：

text
feature(qual_mgmt): 新增回弹仪试验页面
bug(personnel_mgmt): 修复考勤记录分页重复
chore(env): 切换 pzgc 生产 API 地址

交互式提交：pnpm commit ​

项目接入 commitizen（cz-customizable）。推荐一律用 pnpm commit 代替 git commit，按提示选 type、填 scope、写 subject，生成符合上述格式的 message。

强制现状（如实记录）

husky 当前只挂了 pre-commit（lint-staged），没有 commit-msg 钩子——commitlint 规则不会在提交时自动拦截，靠 pnpm commit 流程 + MR 评审保证。直接 git commit -m "xxx" 不会被拦，但会过不了评审。

分支命名规范 ​

分支说明
master生产环境分支，用于发布正式环境的代码，已锁，不可随意修改
stable预发布分支，用于发布开发/测试环境的代码，已锁，不可随意修改
dev/功能名称常规开发分支
hotfix/bug名称紧急 bug 修复，需要立刻合到 master 分支验证
fix/bug名称一般 bug 修复，如 fix/#709-712
feat/功能名称功能模块新增，用于新功能开发，时间要求较缓
refactor/功能名称功能模块重构
perf/优化内容用于性能优化

MR 评审与发布流 ​

  1. 日常流转：dev/* / feat/* / fix/* → 提 MR → 评审通过 → 合入 stable → 随 stable 发布到开发/测试环境验证；
  2. 发布生产：stable 验证通过后合入 master 发布正式环境；
  3. 紧急修复：hotfix/* 从 master 拉出，修复后合回 master 验证，再同步 stable；
  4. 纪律：基于 dev 的分支保持独立干净，一个分支只做一类事；每天先更新远端代码再开发。
