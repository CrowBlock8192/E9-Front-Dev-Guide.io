E9 前端开发指南 · 需求缺口与不足分析 ​

配套 需求文档。本文分析原始需求「三端 × 七板块」中的漏洞与不足，每条按 问题 / 影响 / 建议 三要素展开。结论摘要见文末。

一、内容类缺口 ​

1.1 PC 端缺「入门」总览页 ​

  • 问题：现有 10 篇直接从技术栈开始，默认读者已在 Keystone 上下文中；无平台定位、项目族谱、术语表。原需求七板块中的「入门」实际无对应文档。
  • 影响：新人对「20+ 客户副本是什么关系」「该 clone 哪个仓库」无从下手，只能口口相传。
  • 建议：新建 pc/introduction.md（需求见需求文档 §4.1），作为每端入门页的固定结构样板。

1.2 提交规范只有分支表，缺 commit message 格式 ​

  • 问题：guide/commit-specification.md 仅 19 行分支命名表；而 e9-delivery-ui 实际已配 commitlint + commitizen（cz-customizable，pnpm commit），规则成文于配置而非文档。
  • 影响：规范「存在但不可见」：其他项目（e9-inspection-web 无任何 husky/commitlint）无法照搬；新人不知道有 pnpm commit，直接 git commit 会被 husky 拦截且不知所措。
  • 建议：按需求文档 §4.6 补全 message 格式篇，并以 e9-delivery-ui 的 commitlint 配置为唯一标准。

1.3 技术栈、功能开发两篇过浅，撑不起「七板块」门面 ​

  • 问题：技术栈 26 行纯链接清单；功能开发正文 31 行，实质内容全靠 templates/*.vue 代码内嵌，api 层写法、hooks、组件放置约定均无。
  • 影响：「功能开发」是使用频率最高的篇目，现状无法支撑新人独立开发第一个页面。
  • 建议：需求文档 §4.2 / §4.5 已定充实方案；templates 三模板继续作为代码样例，正文补讲解。

1.4 代码模板仅覆盖 PC Arco 栈，移动端无模板 ​

  • 问题：docs/templates/ 三个模板（list/edit/details）全是 Arco + PC 业务组件风格；移动端（uni-app + uView）无任何模板。
  • 影响：移动端「功能开发」篇落地时无样板可引，各客户项目页面风格继续发散。
  • 建议：templates 按端分目录（需求文档 §7.4）；移动端模板从 delivery-template-uniapp 真实业务页抽取，作为移动端功能开发篇的配套交付物，需与 5.5 同步立项。

1.5 权限 / i18n 深度文档「PC 独有」，移动端对应文档滞留项目内 ​

  • 问题：站点深度的按钮权限、i18n 系列只写了 PC；移动端其实有同主题文档（delivery-template-uniapp/docs/uniapp-button-permission-rule-guide.md 等 6 篇）但躺在项目仓库里未入站。
  • 影响：指南「三端对称」目标落空；移动端知识依赖「知道有那个仓库」这个隐性前提。
  • 建议：按需求文档 §5.6 / §5.7 迁入移动端规范与参考板块；迁移后按 SSOT 原则处理项目内副本（见 2.1）。

二、技术设施类缺口 ​

2.1 移动端工程无提交规范强制设施 ​

  • 问题：delivery-template-uniapp 无 husky、commitlint、eslint 配置；e9-inspection-web 同样裸奔。
  • 影响：PC 端成文的提交规范在移动端无法落地（指南写了也执行不了）；移动端代码风格无门禁。
  • 建议：短期在移动端提交规范篇注明「靠自觉 + MR 评审」；中期给模板工程补 husky + lint-staged + commitlint（与 PC 同配置），随模板派生自然铺开。

2.2 指南站无部署 CI，且部署目标是「双份」的 ​

  • 问题：部署靠手动构建 → 复制产物到 docs/dist/E9-Front-Dev-Guide.io（嵌套 git 仓库，指向 GitHub Pages）→ push；.gitee/ 无任何 CI 配置，config.mts 注释却写 Gitee Pages。两个部署目标并存且无自动化。
  • 影响：发版步骤不可复现、易漏易错；嵌套 git 仓库在主仓库里以 gitlink 形式存在，克隆体验差；两处线上地址可能版本不一致。
  • 建议：二选一定主部署源（团队在 Gitee，建议 Gitee Pages 为主），淘汰嵌套仓库；补一条 CI（Gitee Go 或 GitHub Actions）：push master → build → deploy。

2.3 Node / 包管理器版本约束普遍缺失 ​

  • 问题：除文档站（pnpm 10.19.0）与 beam-web（node >=8.9，形同虚设）外，各项目 package.json 均无 engines 字段；e9-terminal-web 甚至把 pnpm 当依赖安装。
  • 影响：文档站要求 Node 24，而存量项目按老文档可能用 Node 14/16——新人环境错配产生的报错（node-sass、openssl 等）排查成本高。
  • 建议：各篇「快速开始」写明确切验证过的版本；有条件时给各项目补 engines + preinstall 检查；指南站首页给出「每端 Node/pnpm 版本速查表」。

2.4 站点搜索仅中文 locale 配置 ​

  • 问题：local search 只在中文 locale 下配置了翻译文案，英文侧无搜索。
  • 影响：英文读者体验残缺（结合 3.1 的双语策略调整，此项优先级可降低）。
  • 建议：随双语策略一并处理：若英文仅保留核心篇，则为英文 locale 补同款搜索配置即可。

三、工程管理类缺口 ​

3.1 三处文档副本同源不同步（最关键的结构性风险） ​

  • 问题：同一套指南内容存在于三处：本站 docs/guide/、e9tech/keystone-deliver-ui/docs/、weChat-applet/delivery-template-uniapp/docs/，且 keystone 仓库内的版本与站点版本已开始各自演化。
  • 影响：任何一处更新都会造成另两处过期；读者不知哪份是权威；AI 辅助编码（各项目 CLAUDE.md / skills 引用这些文档）可能读到旧规则。
  • 建议：确立站点为 SSOT（需求文档 §8.1）：项目内 docs 发布迁移后改为链接或删除；过渡期在项目内副本头部加「已迁移，以站点为准」横幅。

3.2 移动端项目派生方式粗放 ​

  • 问题：移动端新项目靠「复制整个目录」派生，工作区里已出现：delivery-template-uniapp - 副本（整目录复制）、delivery-template-uniapp.zip（207MB 归档）、查询当前文件夹的git地址.bat 等痕迹；客户项目（changjin 等）与模板的关系无记录。
  • 影响：模板升级无法回灌到已派生项目；磁盘与仓库噪声大；「哪个是权威模板」全靠记忆；207MB 的 zip 若入库是事故。
  • 建议：模板仓库化——delivery-template-uniapp 独立 git 仓库 + 打 tag；派生项目走「clone 模板 → 改 remote → 记录基线 tag」流程；工作区清理副本与 zip（移入归档盘）；PC 端 20+ 客户副本同理核查派生记录。

3.3 废弃 / 无关项目会误导读者 ​

  • 问题：admin-app/e9ech 是 e9tech 的残缺拷贝（无配置无 git）却与 e9tech 仅一字母之差；admin-app/uniapp-admin 是未定制的 DCloud 官方模板，与真实移动端栈（uni-app Vue2 + uView）无关。
  • 影响：读者（及 AI 辅助编码）把废弃目录当代码蓝本，得出错误结论。
  • 建议：入门页项目族谱表标注状态（需求文档 §4.1 已含）；有条件时将废弃目录移出工作区或改名（如 _archived/ 前缀）。

3.4 移动端无 pages.json 生成 / 裁剪脚本，全量分包交付 ​

  • 问题：PC 端多客户靠 VITE_BUILD_VIEWS 编译期裁剪；移动端页面全量打进分包，客户差异完全交给运行时权限与 prefix-rules。
  • 影响：这是现状机制而非缺陷，但意味着：小程序包体积随业务只增不减（主包 2MB 红线风险）；客户 A 的页面代码对客户 B 可见（若涉及敏感逻辑需注意）。
  • 建议：项目结构篇如实记录该机制及体积红线；将「分包体积监控」列入移动端遗留项；如未来需要编译期裁剪再评估脚本方案。

四、流程类缺口 ​

4.1 双语镜像维护不可持续 ​

  • 问题：现状 10 篇 ×2 语言已靠一次性补齐；三端目标 21+ 篇，若每篇都维护英文镜像，翻译工作量翻倍且必然滞后。
  • 影响：英文版长期过期比没有更糟（读者无法分辨新旧）。
  • 建议：中文先行、英文仅核心篇 + 「以中文为准」提示（需求文档 §7.2 已定）；现有英文镜像在对应中文篇大改时同步更新或降级。

4.2 无内容 owner / 评审 / 过期机制 ​

  • 问题：指南无元信息（负责人、最后验证日期），无评审流，git 历史全为「首次提交」无追溯价值。
  • 影响：文档腐化不可见——没人知道某篇是否还与代码一致；新人按过期文档操作踩坑后对指南失去信任。
  • 建议：需求文档 §8.3/§8.4 已定元信息与 MR 评审机制；另建议 git 提交遵循同一套 commit 规范（指南站自己先用起来）。

4.3 三端技术栈代际割裂，升级无规划 ​

  • 问题：PC 主力 Vue3 + Arco / Vite4；移动端 uni-app Vue2 + HBuilderX（工具链与 PC 完全不同）；桌面端 Electron 29 + Vue 2.7（且 Vue2.7 是过渡版本）；存量 PC 还有两套 Vue2 栈。HBuilderX 工程化程度低（无 CLI、依赖管理弱），与 PC 的 pnpm 工作流割裂。
  • 影响：跨端协作成本高；uni-app Vue2 生态在收缩（官方已主推 Vue3/CLI），长期有工具链停更风险；桌面端基于 Vue2.7 新功能开发空间受限。
  • 建议：本期按已确认决策如实记录现状，不按目标态虚构；将「uni-app 迁移 Vue3 + CLI 化」「Electron 升级与前端框架选型」列为独立遗留项，待业务空窗期立项，不在指南内承诺时间表。

结论摘要 ​

优先级事项
高（阻塞指南三端化落地）1.1 PC 入门页 · 1.2 提交规范补全 · 1.5 移动端文档迁入 · 3.1 确立 SSOT
中（影响可用性）1.3 技术栈/功能开发充实 · 2.2 部署 CI · 2.3 版本速查 · 4.1 双语策略
